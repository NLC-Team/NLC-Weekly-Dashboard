# Security posture

Read this before deploying the dashboard anywhere, and before putting real client
data into it.

## There is no authentication

The dashboard has **no sign-in, no accounts and no passwords**. Every page —
including Import, Settings, Audit Log and Delete Clients — is served to anyone who
can open the port. Roles on the Staff page are descriptive labels; they do not
restrict anything.

**Network reachability is the entire access control model.** That is a deliberate
choice for a tool that runs on one machine inside one office's LAN, and it is the
single most important thing to understand about deploying it.

### What that means in practice

- Serve it on an internal network only. `setup/enable-team-access.ps1` opens the
  firewall for the Domain and Private profiles and deliberately excludes Public.
- **Never** expose the port to the internet: no port forwarding, no tunnel, no
  public reverse proxy, no `0.0.0.0` binding on an internet-facing host.
- To restrict the app to the machine it runs on, set `NLC_BIND_HOST=127.0.0.1`.
  That is the right setting for a personal copy on a laptop.
- If it ever genuinely needs to be reachable from outside the office, put a real
  authenticating proxy in front of it first. Do not rely on an obscure URL.

## What the app does protect against

These are still in place and still matter, because they defend against a hostile
*page* rather than a hostile *user*:

- **CSRF tokens** on every state-changing POST, so another site the user has open
  cannot make their browser import or delete data here.
- **A strict Content-Security-Policy** — `script-src 'self'` plus a per-request
  nonce, with no `'unsafe-inline'`. Injected inline script will not execute. (This
  is why event handlers live in `addEventListener` blocks, never in `onclick=`
  attributes; an inline handler added to a template is silently dead code.)
- `X-Frame-Options: DENY`, `nosniff`, a same-origin referrer policy, and a
  request-body cap that rejects oversized uploads with a clean error.
- A signed session cookie, `HttpOnly` and `SameSite=Lax`, keyed by a random
  per-machine secret held outside the database.

## Data at rest

The database is a plain SQLite file, **not encrypted**, at
`%LOCALAPPDATA%\KarbonPendingDashboard\dashboard.db` for whichever account runs
the app. Anyone who can read that file, or a backup of it, can read all client
data in it. Protect it with filesystem permissions and treat backups of it with
the same care as the data itself.

Keep the file on a local disk. SQLite corrupts when the same file is opened over a
Windows file share by several users — copy it to a share for backup, but never run
the app against a share.

## Never commit client data

This repository is public. The dashboard's own Weekly Review exports and any
Karbon export contain named taxpayers, their engagement status, and matters like
audits and delinquent filings. `.gitignore` blocks `*.xlsx`, `*.xls`, `*.db` and
`weekly-review-*.pdf` as a backstop, but the habit matters more than the rule:
keep real exports outside the repository folder.

The fixtures in `sample_data/` are synthetic — generated by the scripts beside
them — and are safe to commit.

## Reporting a problem

This is an internal firm tool rather than a supported product. If you find a
security issue, raise it directly with the maintainer rather than opening a public
issue.
